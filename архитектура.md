# 1. Executive Summary

**grading.hrlab.uz** должна быть не просто HR-калькулятором, а защищённой enterprise SaaS-платформой для проведения грейдинг-проектов HR Laboratories в разных компаниях-клиентах.

Рекомендуемая архитектура:

**Hybrid Modular Architecture**

* на старте: **modular monolith на Java 21 + Spring Boot 3.x**;
* отдельные асинхронные worker-сервисы для импорта, отчётов, AI-assist и интеграций;
* в будущем — возможность выделения отдельных модулей в microservices без переписывания доменной логики.

Ключевое архитектурное решение:

**Hybrid multi-tenancy**

* общий control plane для HR Laboratories: tenants, users, subscriptions, templates, audit registry;
* для данных компаний-клиентов: **schema-per-tenant** как базовая модель;
* для особо чувствительных клиентов: **database-per-tenant**;
* tenant_id обязателен во всех клиентских таблицах как defense-in-depth;
* PostgreSQL RLS + backend tenant validation + ABAC-политики.

Основная цель — исключить любой сценарий, при котором пользователь одной компании-клиента увидит должности, оклады, грейды, отчёты или вложения другой компании-клиента.

# 2. Product Vision

Платформа должна стать цифровым рабочим пространством HR Laboratories для полного цикла грейдинг-проекта:

**от загрузки оргструктуры → анализа должностей → настройки методологии → оценки → калибровки → утверждения грейдов → расчёта вилок → подготовки отчётов.**

Продуктовая ценность для HR Laboratories:

| Направление     | Ценность                                                         |
| --------------- | ---------------------------------------------------------------- |
| Консалтинг      | Единая методология, меньше ручного Excel, выше качество проектов |
| Безопасность    | Изоляция данных компаний-клиентов, аудит, контроль доступа       |
| Масштабирование | Возможность вести десятки проектов параллельно                   |
| Повторяемость   | Шаблоны методологий HR Laboratories                              |
| Аналитика       | Dashboards для консультантов и клиента                           |
| Монетизация     | SaaS-модель: project-based, subscription, enterprise tier        |

# 3. Business Context

Методологическая база платформы должна поддерживать классический цикл грейдинга: подготовка рабочей группы, формирование перечня оцениваемых должностей, описание и анализ должностей, выбор факторов, распределение факторов по уровням, оценка, расчёт баллов, распределение по грейдам, установка окладных вилок и аналитика .

Платформа должна быть универсальной: сегодня клиентом может быть банк, завтра — холдинг, производственная компания, университет, телеком, страховая компания или государственная организация.

Поэтому в доменной модели нельзя жёстко зашивать банковские термины. Например:

* не “банк”, а **компания-клиент**;
* не “головной офис”, а **head office / центральный офис**;
* не “филиал банка”, а **branch / региональное подразделение**;
* не “банковская должность”, а **position / job profile**.

# 4. Key Architecture Principles

1. **Tenant isolation by design**
   Любая сущность с данными компании-клиента должна быть привязана к tenant_id и project_id. Backend не принимает tenant_id как свободный параметр от frontend.

2. **Methodology versioning**
   Утверждённая методология не изменяется. Любое изменение создаёт новую версию.

3. **Human-in-the-loop**
   AI может предлагать оценку, но не утверждает грейд. Финальное решение принимает консультант, проектный менеджер или оценочный комитет.

4. **Audit everything**
   Все изменения по должностям, факторам, оценкам, вилкам, комментариям, правам доступа, экспорту и отчётам должны фиксироваться.

5. **Salary data is special**
   Окладные данные — отдельный класс чувствительности. Даже если пользователь видит должность и грейд, он не должен автоматически видеть оклад.

6. **Configurable, not hardcoded**
   8-факторная модель, 11-критериальная модель, 14/16 грейдов и кастомные модели должны быть конфигурациями, а не отдельными ветками кода.

7. **Multilingual by default**
   Платформа обязательно поддерживает:

   * Русский — `ru-RU`;
   * Ўзбек кирилл — `uz-Cyrl-UZ`;
   * O‘zbek latin — `uz-Latn-UZ`;
   * English — `en-US`.

# 7. Multi-Tenant Architecture

## 7.1 Options comparison

| Model                                 | Description                                          | Pros                                    | Cons                         | Security  | Recommendation                     |
| ------------------------------------- | ---------------------------------------------------- | --------------------------------------- | ---------------------------- | --------- | ---------------------------------- |
| Shared DB + shared schema + tenant_id | Все клиенты в одних таблицах                         | Дешевле, проще аналитика                | Высокий риск ошибки в query  | Medium    | Только для low-risk MVP sandbox    |
| Shared DB + RLS + tenant_id           | Один набор таблиц, PostgreSQL RLS                    | Лучше защита                            | Всё равно общий blast radius | Medium+   | Можно для control plane            |
| Schema-per-tenant                     | Отдельная schema на компанию-клиента                 | Хороший баланс безопасности и стоимости | Миграции сложнее             | High      | **Базовая рекомендация**           |
| Database-per-tenant                   | Отдельная БД на клиента                              | Максимальная изоляция                   | Дороже, сложнее ops          | Very high | Для enterprise / sensitive clients |
| Hybrid                                | Control plane shared, client data schema/db isolated | Баланс гибкости и защиты                | Требует дисциплины DevOps    | Very high | **Итоговая рекомендация**          |

## 7.2 Recommended model for grading.hrlab.uz

**Control Plane — shared database**

* tenant;
* company;
* user identity mapping;
* subscription/license;
* global methodology templates;
* global permissions;
* system audit registry;
* localization dictionaries.

**Data Plane — schema-per-tenant by default**

* `tenant_acme.organization_unit`;
* `tenant_acme.position`;
* `tenant_acme.job_profile`;
* `tenant_acme.evaluation`;
* `tenant_acme.salary_range`;
* `tenant_acme.employee_compensation_snapshot`.

**Premium isolation — database-per-tenant**

* для крупных компаний-клиентов;
* для клиентов с особыми требованиями к комплаенсу;
* для проектов с массовой загрузкой окладов и персональных данных.

Практически это выглядит так:

```text
grading_control_db
  public.tenants
  public.users
  public.client_companies
  public.global_methodology_templates
  public.system_audit_log

grading_client_db
  tenant_001.positions
  tenant_001.job_profiles
  tenant_001.evaluations
  tenant_001.salary_ranges

  tenant_002.positions
  tenant_002.job_profiles
  tenant_002.evaluations
  tenant_002.salary_ranges
```

Дополнительно даже внутри tenant schema все бизнес-таблицы имеют `tenant_id`, потому что это второй уровень защиты.

# 8. Security & Confidentiality Architecture

## 8.1 Identity and authentication

Рекомендуемый подход:

* OAuth2 / OpenID Connect;
* JWT access token;
* refresh token через identity provider;
* Keycloak / Auth0 / корпоративный IdP клиента;
* Spring Security Resource Server.

JWT claims:

```json
{
  "sub": "user-uuid",
  "email": "user@company.uz",
  "active_tenant_id": "tenant-uuid",
  "active_project_ids": ["project-uuid-1"],
  "roles": ["CLIENT_HR_DIRECTOR"],
  "permissions": [
    "POSITION_READ",
    "EVALUATION_APPROVE",
    "REPORT_EXPORT"
  ],
  "salary_data_permission": false,
  "department_scope": ["dept-uuid-1", "dept-uuid-2"],
  "locale": "ru-RU"
}
```

Важно: если HRLab Consultant работает с несколькими компаниями-клиентами, frontend не должен просто отправлять `tenant_id`. Вместо этого backend должен выдавать **short-lived tenant context token** после проверки, что консультант действительно назначен на проект этой компании-клиента.

## 8.2 RBAC + ABAC

**RBAC** отвечает на вопрос: “что в принципе может делать роль?”

**ABAC** отвечает на вопрос: “может ли этот конкретный пользователь выполнить действие над этим конкретным объектом в этом tenant/project/department?”

Пример политики:

```text
User can view Position if:
  user.active_tenant_id == position.tenant_id
  AND project.id IN user.active_project_ids
  AND (
       user.role IN [HRLAB_SUPER_ADMIN, HRLAB_PROJECT_MANAGER]
       OR position.department_id IN user.department_scope
      )

User can view Salary Data if:
  previous condition is true
  AND user.salary_data_permission == true
```

## 8.4 Salary data protection

Окладные данные должны храниться как отдельный sensitive domain.

Защита:

* отдельные permissions: `SALARY_VIEW`, `SALARY_EDIT`, `SALARY_EXPORT`, `SALARY_SCENARIO_RUN`;
* field-level encryption для:

  * current_salary;
  * fixed_pay;
  * variable_pay;
  * benefits_value;
  * total_cash;
  * total_compensation;
* envelope encryption:

  * master key в Vault/KMS;
  * tenant data encryption key per tenant;
  * key rotation;
* все экспорты с salary data логируются отдельно.

## 8.5 Audit log

Audit log должен быть append-only.

Фиксировать:

* login/logout;
* tenant context switch;
* создание/изменение должности;
* изменение профиля должности;
* изменение методологии;
* выбор уровня фактора;
* ручную корректировку балла;
* утверждение оценки;
* изменение грейдовой структуры;
* просмотр salary data;
* экспорт Excel/PDF/Word;
* скачивание вложений;
* изменение прав доступа.

# 13. API Architecture

## 13.1 General API principles

```text
/api/v1/{resource}
```

Не использовать tenant_id как свободный path parameter для клиентских данных.

Правильно:

```http
GET /api/v1/projects/{projectId}/positions
Authorization: Bearer <context-token-with-tenant>
```

Неправильно:

```http
GET /api/v1/tenants/{tenantId}/projects/{projectId}/positions
```

Исключение — HRLab Super Admin endpoints в control plane, но только с отдельными permissions.

# 15. Scoring & Grading Engine

## 15.1 Supported methodology types

1. **Classic 8-factor / 1000-point model**
   Методология должна поддерживать 8 факторов: образование, опыт, управление, решение проблем, ответственность, коммуникация, условия работы, зона влияния. В источниках есть пример 1000-балльного подхода и факторных максимальных баллов .

2. **Extended 11-criteria model**
   Расширенная модель должна поддерживать 11 критериев: образование и опыт, уникальность квалификации, функциональное и административное подчинение, внутренняя и внешняя коммуникация, инновации, сложность анализа информации, роль в методологии, свобода решений, финансовое влияние. Такая модель присутствует в проектных материалах с весами и уровнем влияния критериев .

3. **Custom configurable model**
   Клиентская методология: кастомные факторы, уровни, веса, баллы, формулы, версии.

## 15.2 Scoring modes

```text
DIRECT_POINTS
  selected level already has points
  total_score = sum(level.points)

WEIGHTED_POINTS
  normalized_score = selected_level.points / factor.max_level_points
  factor_score = normalized_score * factor.weight_points
  total_score = sum(factor_score)

WEIGHTED_SCALE
  factor_score = selected_level.scale_value * factor.weight
  total_score = sum(factor_score)

FORMULA_BASED
  controlled expression engine
  total_score = formula(context)
```

## 15.3 Evaluation algorithm

```text
1. Load approved methodology version.
2. Load active factor list.
3. For each factor:
   - validate selected level;
   - calculate factor score;
   - store raw score;
   - store displayed score;
   - store evaluator and comment.
4. Sum factor scores.
5. Apply rounding rules.
6. Find grade band:
   grade_band.min_score <= total_score <= grade_band.max_score.
7. Store evaluation snapshot.
8. Generate audit events.
9. Lock evaluation after approval.
```

## 15.4 Rounding rules

* хранить баллы как `NUMERIC(12,4)`;
* отображать до 2 знаков;
* grade assignment делать по raw score, а не по округлённому значению;
* границы грейдов не должны пересекаться;
* validation rule: no gaps, no overlaps.

## 15.5 Missing values

| Case                                  | Rule                                          |
| ------------------------------------- | --------------------------------------------- |
| Required factor missing               | Evaluation status = incomplete                |
| Optional factor missing               | Score = 0 or excluded by methodology setting  |
| Not applicable factor                 | Must be explicitly marked as N/A with comment |
| Approval with missing required factor | Forbidden                                     |
| AI suggested but human not confirmed  | Not counted as final score                    |

## 15.6 Methodology change

Утверждённая методология locked. При изменении:

1. создаётся новая version;
2. старые evaluations остаются привязанными к старой version;
3. можно запустить recalculation scenario;
4. результаты сравниваются как `old_score`, `new_score`, `delta`;
5. массовое применение требует approval.

# 16. Salary Range & Compensation Engine

Модуль должен поддерживать минимальную, среднюю и максимальную вилку оклада по грейдам, категорию персонала, комментарий и рыночный коэффициент — такая структура присутствует в шаблонах оценки должностей и вилок .

## 16.1 Core formulas

```text
compa_ratio = current_salary / midpoint

range_penetration =
  (current_salary - range_min) / (range_max - range_min) * 100

red_circle =
  current_salary > range_max

green_circle =
  current_salary < range_min

budget_impact =
  target_salary - current_salary
```

## 16.2 Salary range model

```text
Grade 7
  minimum: 8,000,000
  midpoint: 10,000,000
  maximum: 12,000,000
  market_coefficient: 1.10
  internal_coefficient: 1.00
  fixed_variable_ratio: 70/30
```

## 16.3 Scenario types

| Scenario            | Purpose                                                  |
| ------------------- | -------------------------------------------------------- |
| Conservative        | Only green circle correction                             |
| Balanced            | Bring employees to minimum + selective midpoint movement |
| Market alignment    | Adjust ranges by market coefficient                      |
| Full implementation | Move all to target range                                 |
| Phased transition   | 6/12/18-month transition                                 |

## 16.4 Recommendations engine

Examples:

```text
If salary < min:
  recommendation = "Increase to range minimum"
  priority = high

If salary between min and midpoint:
  recommendation = "Normal progression zone"

If salary > max:
  recommendation = "Red circle: freeze base pay, use lump-sum bonus"

If compa_ratio between 0.8 and 1.2:
  recommendation = "Within acceptable range"
```

# 25. Architecture Decision Records

## ADR-001: Multi-tenant model

Decision: Hybrid model: shared control plane + schema-per-tenant by default + database-per-tenant for sensitive clients.
Reason: strong isolation without excessive cost.
Consequence: migrations must support multiple schemas.

## ADR-002: Backend stack

Decision: Java 21 + Spring Boot 3.x.
Reason: enterprise maturity, security ecosystem, strong typing, good fit for HR/finance workflows.
Consequence: team must follow strict modular boundaries.

## ADR-003: Architecture style

Decision: Hybrid modular architecture.
Reason: modular monolith for core domain, workers for heavy async tasks.
Consequence: future microservice extraction remains possible.

## ADR-004: Database

Decision: PostgreSQL.
Reason: relational integrity, JSONB where needed, RLS, strong indexing.
Consequence: need careful schema migration governance.

## ADR-005: Migration tool

Decision: Liquibase.
Reason: better enterprise multi-schema lifecycle and rollback control.
Consequence: changelog discipline required.

## ADR-006: Security model

Decision: OAuth2/OIDC + JWT + RBAC + ABAC.
Reason: role alone is insufficient for tenant/project/department/salary restrictions.
Consequence: policy layer required in backend.

## ADR-007: Salary encryption

Decision: field-level encryption with tenant-specific keys.
Reason: salary data is highly sensitive.
Consequence: analytics needs controlled decryption or precomputed aggregates.

## ADR-008: Audit strategy

Decision: append-only audit log with hash chaining.
Reason: evaluations and salary changes must be traceable.
Consequence: audit storage grows and needs retention strategy.

## ADR-009: Reporting

Decision: async report generation via worker.
Reason: PDF/Word/Excel reports can be heavy.
Consequence: report status tracking required.

## ADR-010: AI integration

Decision: AI Gateway with masking, policy checks, logging.
Reason: client data confidentiality and explainability.
Consequence: AI is advisory, not decision-maker.

## ADR-011: File storage

Decision: S3-compatible object storage with tenant/project namespace and signed URLs.
Reason: scalable storage for Excel, Word, PDF, job descriptions.
Consequence: attachment access must always pass backend authorization.

## ADR-012: Localization

Decision: 4-language support from MVP architecture level.
Reason: platform must support Russian, Ўзбек, O‘zbek and English from the beginning.
Consequence: dictionaries, methodology descriptions and report templates must be translatable.

## ADR-013: Super-admin in-place edit of APPROVED methodology versions

Decision: relax the §4 #2 / §15.6 immutability invariant for APPROVED versions
only — a super admin (`METHODOLOGY_EDIT_APPROVED`) may edit scoring fields in
place; LOCKED/ARCHIVED stay hard-immutable; `scoring_mode` excluded.
Reason: avoid forcing a full new-version migration for every scoring correction
while keeping already-scored evaluations reproducible.
Consequence: reproducibility is weakened-but-recorded — guaranteed by a
per-evaluation immutable basis snapshot + soft-deprecate + RESTRICT FKs and a
per-field + `METHODOLOGY_APPROVED_EDIT` umbrella audit trail.
Full record: [`docs/adr/ADR-013-super-admin-edit-approved-methodology-version.md`](docs/adr/ADR-013-super-admin-edit-approved-methodology-version.md).

# 26. Final Recommendations

1. **Start with modular monolith, not microservices.**
   Грейдинг-процесс tightly coupled: methodology, scoring, workflow, audit and reporting need strong consistency.

2. **Adopt hybrid multi-tenancy.**
   Для grading.hrlab.uz лучшая модель — shared control plane + schema-per-tenant, with database-per-tenant for enterprise clients.

3. **Build tenant isolation into every layer.**
   JWT context, backend policy, repository filters, PostgreSQL RLS, object storage namespace, report generator scope.

4. **Treat salary data as a separate security domain.**
   Нельзя смешивать доступ к грейдам и доступ к окладам.

5. **Make methodology versioning non-negotiable.**
   Утверждённая методология должна блокироваться. Изменения — только через новую версию.

6. **Design the scoring engine as configurable.**
   8 факторов, 11 критериев, 14/16 грейдов и кастомные модели должны работать через единый engine.

7. **Implement audit trail from MVP 1.**
   Audit нельзя “добавить потом”, потому что он должен фиксировать жизненный цикл данных с первого дня.

8. **Add multilingual architecture immediately.**
   Русский, Ўзбек кирилл, O‘zbek latin и English должны быть частью data model, UI и report templates.

9. **Use AI only as assistant.**
   AI может помогать анализировать должностные инструкции, предлагать уровни факторов и выявлять аномалии, но не утверждать грейды.

10. **Make tenant isolation tests release gate.**
    Ни один релиз не должен попадать в production, если tests не доказывают, что данные одной компании-клиента недоступны другой компании-клиенту.
